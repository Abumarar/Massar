1. Project Overview 
1.1 Introduction 
Tawsileh Intercity is a ride-sharing and passenger aggregation mobile application designed 
specifically for intercity transportation in Jordan. 
Unlike conventional ride-hailing applications, where one passenger typically pays the full 
trip cost, Tawsileh allows multiple passengers traveling along compatible routes to share 
the same vehicle and divide the trip cost. 
The prototype will initially focus exclusively on the: 
Jerash ↔ Amman 
route. 

--- PAGE 2 ---
The system will match passengers with captains whose predefined route is compatible 
with the passenger's pickup location and destination. 
The initial vehicle capacity supported by the system is: 
Maximum: 4 passengers per trip. 
The fundamental objective is to reduce the individual transportation cost for passengers 
while allowing captains to serve multiple passengers during the same intercity journey. 
 
2. Problem Statement 
Intercity transportation in Jordan can be relatively expensive when a passenger requires a 
private ride. 
For example: 
A private trip from Jerash to Amman may cost approximately: 
12 JOD 
A single passenger therefore pays the entire amount.

3. Product Vision 
Tawsileh aims to become an intercity shared transportation platform connecting 
passengers traveling between Jordanian cities. 
The long-term vision is: 
Make intercity transportation more affordable by intelligently combining passengers 
traveling along compatible routes. 
The system should eventually support: 
• Jerash ↔ Amman 
• Irbid ↔ Amman 
• Zarqa ↔ Amman 
• Ajloun ↔ Amman 
• Salt ↔ Amman 
• Madaba ↔ Amman 
• Other intercity routes 
However, the prototype must only implement: 
Jerash ↔ Amman 
 
4. Prototype Objectives 
The prototype must prove that the following process works: 
1. Passenger opens the application. 
2. Passenger selects pickup location. 
3. Passenger selects destination. 
4. Passenger submits a ride request. 
5. System identifies compatible captain routes. 
6. System evaluates route compatibility. 
7. System checks pickup/destination proximity. 
8. System checks available seats. 

--- PAGE 4 ---
9. System ranks compatible captains. 
10. Passenger receives available matches. 
11. Captain receives the ride request. 
12. Captain accepts the passenger. 
13. Passenger sees captain information and location. 
14. Captain picks up passenger. 
15. Trip begins. 
16. Trip is completed. 
17. Available seats are updated.

39. Matching Engine 
The Matching Engine is the core business component. 
The system should not simply search for the nearest captain. 

--- PAGE 27 ---
It should search for: 
Captains whose predefined route is geographically compatible with the passenger's 
journey. 
 
40. Route Model 
Each captain has a route represented as a geographic polyline. 
Example: 
Jerash 
   | 
   | 
   | 
Amman 
 
Internally: 
Route 
    └── geometry: LINESTRING(...) 
 
PostGIS stores this geometry. 
 
41. Passenger Journey Model 
The passenger journey contains: 
pickupPoint 
destinationPoint 
 
Both are geographic points. 

--- PAGE 28 ---
The matching system evaluates both against the captain's route. 
 
42. Basic Matching Rules 
A captain is eligible if: 
Rule 1 — Same Direction 
Passenger journey must correspond to the captain's direction. 
Example: 
Passenger: 
Jerash → Amman 
 
Captain: 
Jerash → Amman 
 
MATCH 
 
But: 
Passenger: 
Jerash → Amman 
 
Captain: 
Amman → Jerash 
 
should not be treated as the same direction. 
 
Rule 2 — Available Seats 
Captain must have enough seats. 

--- PAGE 29 ---
If passenger requests: 
2 seats 
Captain must have: 
>= 2 available seats 
 
Rule 3 — Pickup Distance 
The passenger's pickup point must be within the captain's allowed pickup radius from the 
route. 
Example: 
Distance from route = 1.2 km 
Captain radius = 3 km 
 
MATCH 
 
 
Rule 4 — Destination Compatibility 
Passenger destination should also be sufficiently close to the captain's route. 
Example: 
Destination distance = 1.0 km 
Maximum allowed = 3 km 
 
MATCH 
 
 

--- PAGE 30 ---
Rule 5 — Detour 
The system should estimate whether serving the passenger creates an unacceptable 
detour. 
This becomes increasingly important when multiple passengers are already onboard. 
 
43. Matching Score 
Each eligible captain receives a score. 
Example: 
Match Score = 
 
Route Compatibility       40% 
Pickup Distance           25% 
Destination Distance      20% 
Available Seats           10% 
Detour                    5% 
 
The exact weights should be configurable.

45. Route Corridor 
The prototype should conceptualize each route as a corridor. 
Example: 
         Allowed area 
       <---------------> 
               Route 
------------------------------- 
               Route 
------------------------------- 
       <---------------> 
          Allowed area 
 
If: 
Captain pickup radius = 3 km 
 
then the system considers passengers within approximately 3 km of the route. 

--- PAGE 32 ---
This concept should later evolve into more sophisticated route deviation calculations. 
 
46. Important Matching Constraint 
The system must not match based purely on straight-line geographic distance. 
Example: 
Two locations may be geographically close but separated by roads that require a large 
detour. 
Therefore: 
Road distance and route compatibility should eventually take priority over simple 
Euclidean distance.

81. Dynamic Trip Matching 
A captain does not necessarily need to wait for exactly four passengers before starting. 
Possible states: 
1/4 seats occupied 
2/4 seats occupied 
3/4 seats occupied 
4/4 seats occupied 
 
The captain may begin according to the business rules defined later. 
 
82. Important Prototype Simplification 
For the first prototype: 
Do not implement complex multi-passenger route optimization. 
Instead: 
1. Captain defines route. 
2. Passenger defines journey. 
3. System checks compatibility. 
4. Passenger joins. 
5. Seat count decreases. 
Once the basic model works, a more advanced algorithm can optimize multiple pickups 
and destinations.

125. Final Recommendation 
The most important part of Tawsileh is not the map UI, login system, or even the mobile 
application itself. 
The core intellectual/technical component is the: 
Route-Based Passenger Matching Engine 
The architecture should therefore be designed around: 
Passenger Journey 
        + 
Captain Route 
        + 
Geographic Compatibility 
        + 
Available Capacity 
        + 
Detour 
        ↓ 
     MATCH SCORE 
 
The first version should remain intentionally simple. 
The goal is not to build a complete Uber competitor. 
The goal is to prove one thing: 

--- PAGE 81 ---
Can Tawsileh reliably find multiple passengers and captains traveling along 
compatible intercity routes and combine them into a shared trip while reducing the 
cost per passenger? 
If the answer is yes, the same architecture can subsequently be expanded from: 
Jerash ↔ Amman 
to a nationwide intercity transportation network.
